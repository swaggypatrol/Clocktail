# Memory (GDDR7)
What the memory offset does and does not buy, its units, and the trap that comes with writing it.

- The memory offset is a P0 offset (MHz). The reference card's daily profile uses **+358 MHz**: memory clock 13801 -> 14159 MHz as NVML reports it.
- **NVML reports twice the real offset** (+358 shows as +716). Clocktail's readings are the real value.
- What it buys on the reference card: **latency, not bandwidth.** +0 / +179 / +358 gave 1437 / 1440 / 1439 GB/s, and 531 / 524 / 518 ns per hop (-2.4 %). Later runs at +358: 1454-1461 GB/s, 504-509 ns.
- The +358 value was carried over from an earlier hand tune, not searched for. Nobody has measured where this card's memory gives out; treat higher values as untested.
- **Writing the memory offset zeroes every V/F point offset** (it is a P0 write). The curve must be written again afterwards. Presets and the daily profile apply it before the curve, so loading one is safe; a hand-made change is not.
- Memory errors show up as artefacts or as a data error in `stress_test` (exit code 6), not always as a crash.
- `set_memory_offset` changes it as a trial (at most 250 MHz per call; the curve is written back right after). How to step it and judge it: `manual method`, phase 7.
- **The sweep (`tune_memory`, ST02).** GDDR7 hides its errors by retrying them (EDR), so past its edge the memory gets slower before it fails. The sweep raises the offset a step at a time (50 MHz by default), each a trial, and has the lab measure each step at one fixed buffer: bit errors, bandwidth in five access orders (linear, 64 KiB and 128 KiB strides, block-xor, permute), latency. It stops at a failure, or where the memory gets slower and stays slower: bandwidth 0.5 % under the best step at two steps in a row, or latency 1 % over the lowest and rising again after a step that rose too. One slower step is only watched (the log says "watching"), because the memory changes its timings at some clocks and one run can be noise. The best offset is the step before the slowdown began. Latency is the signal that follows the DRAM (531 → 518 ns for +0 → +358 on the reference card); bandwidth only must not fall, because the crossbar can hold it (flat 1437-1440 GB/s from +0 to +358 at XBAR +250).
- **What the reference card showed (2026-10-22, on the uncore XBAR +400 / +50 mV, ratio 0.95, MSVDD REL +50 / ALT +30).** +358 to +3000 in 100 MHz steps, 30 s each, three times over the day: no errors at any step, the memory clock following the offset 1:1 in P1. Bandwidth climbed with the clock to about +1758 (1693 → 1795 GB/s) and then went sideways to +3000 (1787-1822, within the spread); with the uncore raised the crossbar no longer held it. Latency fell with every step, 475 → 429 ns, but for one jump: 460.6 → 477.7 ns at +958, the same in all three sweeps, then falling with the clock again (a timing change, which the old one-step rule read as the edge). Bandwidth dipped once at +1558 in all three too (-0.9 to -1.2 %). The spread between runs grew with the offset, ~1 % at +358, 4-5 % from +1458, 6-9 % past +2700. The sweep stopped at +3000 (bandwidth under +2858's at +2958 and +3000); a fine sweep +2768 to +2948 in 30 MHz steps, 60 s each, read 1782-1802 GB/s (flat within the spread) and 433.5 → 429.7 ns. Past ~+1758 an offset buys latency only (~2.2 ns per 100 MHz), not bandwidth.
- **What decided it: their benchmarks, not the lab's best reading.** The person ran 3DMark at +358, +1758 and +2900+: Speedway (ray tracing, the memory-sensitive one) was a little better at +1758 than at +358, Steel Nomad barely moved, and +2900 beat +1758 in neither. So the lab's "best" (+2858, the highest single reading on a flat plateau) was the wrong pick, and the latency it bought (-6 %) never reached a frame: a GPU hides memory latency with thousands of threads in flight and its L2. The reference card's daily is +1758.
- **30 MHz steps from +1458 to +2058** (21 points, 60 s each): no error, no timing change (latency fell 464.3 → 449.5 ns in a straight line, ~0.75 ns per 30 MHz), bandwidth flat from about +1550 (~1790 GB/s, every step within the spread). The +1558 dip of the coarse sweeps did not show at +1548 or +1578.
- **Round numbers do not matter.** +1740, +1755, +1770, +1785, +1800 against +1758, each twice in a mirrored order: 1788.9-1792.2 GB/s, within the spread of +1758's own three runs (1790.3-1795.4); NVML's memory clock followed every offset 1:1. Nothing about GDDR7 here wants a multiple of 15 or 30.
- **How to choose, then:** where bandwidth stops rising (read the steps; the sweep's own "best" is only the edge's side), not the lowest latency. Confirm it against the daily offset with a memory-sensitive benchmark run A B B A (a ray-traced one: Speedway, or a ray-traced game's benchmark; Steel Nomad judges the core, not the memory). One run each is not enough: 3DMark moves 0.5-1 % from one run to the next, as much as the gain.
- **What it needs.** An open session with no trial in force, and an otherwise idle GPU: a local AI model, a game or a screen saver sharing the GPU makes speeds meaningless (on the reference card a local llama-server moved the bandwidth by 20 %, and Windows' Mystify screen saver kept the GPU 22 % busy and cost DRAM 21 % and the L2 test 19 %). The lab calls a run shared when others hold over 4 GiB of video memory, keep the GPU over half busy before its load, or over 10 % just after it while the clocks are still up (utilization is time, so it reads by the clock: the idle desktop read 12-15 % at idle clocks and 2-3 % just after a run, Mystify 21-25 %), and a job measures a shared run again every 30 s for up to 10 minutes: a screen saver draws until the display sleeps. For a run overnight, set the screen saver to none or let the display sleep sooner. CUDA work alone ran in P1 there, also with Boost Lock held (it holds P0 only at idle), and the memory offset is a P0 offset; whether it acts in P1 is not measured yet. So every step checks that NVML's memory clock rose with the offset: if it did not, the sweep stops and says the offset was not in force. A curve on the card that Clocktail does not hold (after `stock`, the curve it found) blocks every memory write: `load_daily` first, or a `set_curve` trial.
- `tune_memory ... trend=true` does not stop at a slower step, only at a failure, a shared GPU or an offset not in force: it draws the whole curve of bandwidth and latency against the offset, to the driver's limit if need be; the best is still the step before the first slower one.
- `lab_test` with `phases=memory,latency` measures the memory once, at whatever offset is on the card, and compares it with the last run at the same offset, buffer and P-state (`memory_vs_last`): a drop at the same setting is the memory retrying, or a hotter card.
- **Memory temperature:** `memory_c` in `gpu_status`, the P10/P50/P90 of `stress_test` and `watch`, and every CSV. It is the memory chip temperature (HWiNFO's "memory chip", in whole degrees), not the junction, which reads about 4 °C hotter at idle and meets it at the peak. On the reference card: 52 °C idle, 80 °C after 90 s of full load, 82 °C at the peak. Watch it while raising the offset: a memory step that only fails warm shows up here first.
