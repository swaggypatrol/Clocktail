# Memory (GDDR7)
What the memory offset does and does not buy, its units, and the trap that comes with writing it.

- The memory offset is a P0 offset (MHz). The reference card's daily profile uses **+358 MHz**: memory clock 13801 -> 14159 MHz as NVML reports it.
- **NVML reports twice the real offset** (+358 shows as +716). Clocktail's readings are the real value.
- What it buys on the reference card: **latency, not bandwidth.** +0 / +179 / +358 gave 1437 / 1440 / 1439 GB/s, and 531 / 524 / 518 ns per hop (-2.4 %). Later runs at +358: 1454-1461 GB/s, 504-509 ns.
- The +358 value was carried over from an earlier hand tune, not searched for. Nobody has measured where this card's memory gives out; treat higher values as untested.
- **Writing the memory offset zeroes every V/F point offset** (it is a P0 write). The curve must be written again afterwards. Presets and the daily profile apply it before the curve, so loading one is safe; a hand-made change is not.
- Memory errors show up as artefacts or as a data error in `stress_test` (exit code 6), not always as a crash.
- `set_memory_offset` changes it as a trial (at most 250 MHz per call; the curve is written back right after). How to step it and judge it: `manual method`, phase 6.
- **The sweep (`tune_memory`, ST02).** GDDR7 hides its errors by retrying them (EDR), so past its edge the memory gets slower before it fails. The sweep raises the offset a step at a time (50 MHz by default), each a trial, and has the lab measure each step at one fixed buffer: bit errors, bandwidth in five access orders (linear, 64 KiB and 128 KiB strides, block-xor, permute), latency. It stops at a failure, or at latency that rises or bandwidth that falls against the best step so far; the best offset is the step before. Latency is the signal that follows the DRAM (531 → 518 ns for +0 → +358 on the reference card); bandwidth only must not fall, because the crossbar set it there (flat 1437-1440 GB/s from +0 to +358, while XBAR +250 raised it to 1474). It runs in the background (`lab_status` follows it, `lab_stop` ends it), puts the daily profile back at the end and keeps nothing: set the best offset with `set_memory_offset`, play, `keep_as_daily` (ask); if a game fails, one step lower.
- **What it needs.** An open session with no trial in force, and an otherwise idle GPU: a local AI model, a game or a screen saver sharing the GPU makes speeds meaningless (on the reference card a local llama-server moved the bandwidth by 20 %, and Windows' Mystify screen saver kept the GPU 22 % busy and cost DRAM 21 % and the L2 test 19 %). The lab calls a run shared when others hold over 4 GiB of video memory, keep the GPU over half busy before its load, or over 10 % just after it while the clocks are still up (utilization is time, so it reads by the clock: the idle desktop read 12-15 % at idle clocks and 2-3 % just after a run, Mystify 21-25 %), and a job measures a shared run again every 30 s for up to 10 minutes: a screen saver draws until the display sleeps. For a run overnight, set the screen saver to none or let the display sleep sooner. CUDA work alone ran in P1 there, also with Boost Lock held (it holds P0 only at idle), and the memory offset is a P0 offset; whether it acts in P1 is not measured yet. So every step checks that NVML's memory clock rose with the offset: if it did not, the sweep stops and says the offset was not in force. A curve on the card that Clocktail does not hold (after `stock`, the curve it found) blocks every memory write: `load_daily` first, or a `set_curve` trial.
- `tune_memory ... trend=true` does not stop at a slower step, only at a failure, a shared GPU or an offset not in force: it draws the whole curve of bandwidth and latency against the offset (up to 2000 MHz past the first offset); the best is still the step before the first slower one.
- `lab_test` with `phases=memory,latency` measures the memory once, at whatever offset is on the card, and compares it with the last run at the same offset, buffer and P-state (`memory_vs_last`): a drop at the same setting is the memory retrying, or a hotter card.
- **Memory temperature:** `memory_c` in `gpu_status`, the P10/P50/P90 of `stress_test` and `watch`, and every CSV. It is the memory chip temperature (HWiNFO's "memory chip", in whole degrees), not the junction, which reads about 4 °C hotter at idle and meets it at the peak. On the reference card: 52 °C idle, 80 °C after 90 s of full load, 82 °C at the peak. Watch it while raising the offset: a memory step that only fails warm shows up here first.
